# 页面类型与页面级模式

同一类页面反复出现：提问页、核对页、确认页、失败页、起始页。它们有稳定的结构，可以直接套；产品经理常犯的错是每做一个都重新发明一遍。

## 1. 问题页（一问一页）

适合长表单、需要准确输入、用户可能中途离开的场景。

- 一页只问一件事，页面标题就是这个问题。
- 必备：返回链接、页面标题、继续按钮；浏览器返回键也要正常。
- 可选字段标「（选填）」；不要用星号标必填。
- 提示文案一句话、不加句号；长解释放正文，不要塞进 hint。
- 允许「不知道 / 不确定」作为有效答案。
- 同一旅程不重复问同一信息，能预填就预填。

## 2. 核对答案页

提交前的最后一道确认，适合中低频、错误代价高的操作。

- 用摘要列表分组展示「问题 → 答案 → 修改」。
- 每行「修改」带隐藏文本（读屏不能听到一串「修改」）。
- 修改后回到核对页，已填内容预填；改动引发新问题时先问完再回来。
- 未填的可选项显示「未提供」。
- 提交按钮写清动作，不要只写「提交」。

## 3. 确认页

交易/提交完成后的页面，让用户安心并知道接下来会发生什么。

必须包含：参考号（如有）、接下来会发生什么及时间、联系方式、后续需要的链接、反馈入口、保存记录的方式（打印/截图/邮件）。

- 用户会把确认页当收据收藏，尽量允许重新访问；不能访问时给有帮助的说明。
- 确认面板里放链接/按钮要注意对比度（至少 3:1），否则可访问性不达标。
- 不要把「提交成功」当成结束：用户下一步要做什么，写清楚。

## 4. 起始页

服务的入口页，回答「这是什么、我能不能用、从哪开始」。

- 服务名 + 一句话说明 + 「开始」按钮。
- 开始前需要准备什么（证件、材料、时间）提前说。
- 处理时间、费用、资格限制等关键信息放在这里，不要藏到流程中段。

## 5. 前置判断页

先用少量问题判断用户是否适用，避免用户填完一长串才发现不符合。

- 不符合时给替代方案或下一步，而不是一句「你不符合条件」。
- 判断逻辑要可解释：告诉用户是基于哪一条不符合。
- 不要让判断页变成营销问卷。

## 6. 任务清单 / 分步导航

适合包含多个子任务、用户会分批完成的流程（开户、申报、入驻）。

- 任务列表显示「已完成 / 待完成 / 进行中」，让用户知道还剩多少。
- 每项任务可独立进入、独立完成；返回列表时状态更新。
- 分步导航适合政策、流程类内容：把长内容拆成步骤，标出当前步。
- 进度指标只在用户真的需要时展示；不要为了「有进度条」而加。

## 7. 错误与异常页面

| 页面 | 必备内容 |
|---|---|
| 404 页面不存在 | 说明找不到 + 搜索框 + 常用链接；不要只放插画 |
| 服务不可用 | 何时恢复、替代渠道（电话/线下）、是否会丢失已填内容 |
| 服务故障（500） | 发生了什么、错误码、重试、联系方式；不暴露技术堆栈 |
| 中断页 | 暂停流程告知重要信息；给「继续」与「退出/保存」两条路 |

共同原则：**说清发生了什么 + 用户还能做什么**。错误页不是终点，要给出路。

## 8. Cookie 与隐私页

- 按用途分类说明（必要 / 分析 / 营销），不要一锅端。
- 接受与拒绝同样显著，不能把「拒绝」做成灰色小字。
- 可随时更改选择；更改入口在页脚可见。
- 不要用「继续浏览即同意」替代明确选择（视地区法规而定）。

## 9. 快速离开（敏感场景）

面向家暴、医疗、举报等敏感服务：提供一键离开按钮，跳到中性页面（如天气），并清理返回历史。

- 按钮在每页固定位置、易发现。
- 离开后不要留下可被「返回」找回的记录。
- 与隐私/安全团队确认实现方式。

## 10. 联系与帮助页

- 给具体渠道、服务时间、响应预期。
- 能自助的先给自助入口（FAQ、状态查询），再给人工。
- 表单类联系页按第 `forms.md` 的规则做，不要让用户重复描述已经提供的信息。

## 验收清单

- [ ] 页面类型明确，用户一眼知道「这是什么页、要做什么」
- [ ] 主操作唯一且文案写清结果
- [ ] 异常页给出下一步，而不是死胡同
- [ ] 关键信息（费用、时限、资格）在开始前出现
- [ ] 完成页给参考号与后续步骤
- [ ] 敏感场景有安全退出路径
