# 交互走查方法

走查的目标不是"证明我懂规范"，而是让作者在有限时间里改对最值得改的地方。

## 1. 取证

按可靠性排序：

1. **代码证据**：事件处理、状态分支、条件渲染、disabled/loading/error、键盘处理、请求错误处理。报告里给 `文件:行号`。
2. **运行证据**：真的走一遍主路径 + 一条错误路径（断网、接口 500、超时）+ 一条中断路径（刷新、返回、重复提交）。记录实际看到什么。
3. **截图证据**：只能说明"某一时刻长什么样"，标清位置与状态（"提交后 0.5 s，页面顶部"）。
4. **口述/需求文档**：作为场景依据，不作为行为证据。

**运行时证据至少覆盖这些动作**，并记下实际看到什么：

- 桌面一档 + 移动两档视口（如 1440 / 390 / 320），看溢出、裁切、吸顶与触控目标；
- 同一路由的 URL 变体（`?tab=`、`?view=`、筛选状态）与兄弟入口成对走：并排截图比页头（返回入口、页标题、页级操作）的相对位置，可用返回链接与标题的 `top` 坐标判断是否同一行；
- 键盘-only 走一遍主任务：Tab 顺序、Enter/Escape、焦点可见、返回后的焦点；
- 站内返回与浏览器返回各一次：筛选、已加载批次、滚动位置是否恢复；
- 中断：流程中刷新、后退、重复提交；
- 失败注入：断网、接口 500、慢响应，看旧内容是否保留、文案是否可执行、能否重试；
- 有要求时看 prefers-reduced-motion 与深色模式；真机、读屏器未测就写未测。

**数据驱动页面先记数据形态**：当前是空、少量、过期、部分失败、无权限、无对照期、未来时间中的哪些。依赖特定数据形态的结论要标「当前形态」，形态覆盖不到时进「需确认」，不要用「页面是空的」推断「功能坏了」。能造 fixture 时先造最小样本（过期快照、无对照期、折叠差异、同文标题）再定级。

拿不到证据时，把结论降级为问题：写"需确认：请求失败时是否有重试入口？建议在 `handleSave` 的 catch 分支确认"。这比断言"没有重试"更专业，也更容易被接受。

### 静态走查（只有代码）

没有可运行页面时，仍然可以做有价值的走查，但要说清边界：

- 报告开头写"本次为静态走查，未运行页面；动效、真实请求与焦点顺序未验证"。
- 能确认的：事件绑定、状态分支是否齐全、请求是否有错误处理、语义元素与标签、键盘处理、条件渲染覆盖。
- 只能标"需确认"的：视觉状态（CSS 在别处）、触控热区尺寸、实际焦点顺序、后端是否接受空值、接口返回结构。
- 顺手检查"看着像交互问题、其实是代码 bug"的点，它们往往是最贵的 P0：
  - 事件处理函数是否真的定义（`select`、`deleteAccount` 这类未定义函数会让点击直接报错）。
  - `fetch` 是否有 `try/catch`；`Content-Type` 是否与 body 类型匹配：JSON 用 `application/json`，`FormData` 不要手写（浏览器要自动带 boundary），`URLSearchParams` 用 `x-www-form-urlencoded`。缺头部在多数后端会导致解析失败，但不是普适必然。
  - 成功判定是否只看 `res.ok`：HTTP 200 + 业务错误码被当成成功，是"看起来存了、其实没存"的常见来源。
  - 是否有状态复位：成功标志位只置真不置假，会让第二次操作永久禁用。
  - 是否有响应时序问题：请求无取消、响应不校验新鲜度，旧结果覆盖新结果（用请求序号或 `AbortController` 丢弃过期响应）。
  - 是否有状态快照问题：React 等渲染快照模型中，handler/effect 可能捕获旧 state（检查依赖数组、函数式更新、`useRef`）；Vue 的 `ref` 通常读到最新值，不要把它当跨框架通用竞态。
  - 是否有超时：`AbortController` 本身不提供超时，要配 `AbortSignal.timeout(ms)` 或 `setTimeout` + `abort()`；否则慢网会一直停在"进行中"。

## 2. 严重度

| 级别 | 判定 | 例子 |
|---|---|---|
| P0 | 主任务无法完成、数据丢失、不可恢复、明显伤害用户 | 提交按钮永远禁用；删除无二次确认也无撤销；失败后表单被清空；提交了未通过校验的数据；失败却显示成功 |
| P1 | 明显摩擦、误解，用户会做错或绕路 | 有幂等/可恢复的重复提交；错误只说"失败"；空状态没有下一步；依赖 hover 才能发现的功能 |
| P2 | 打磨项，影响体验质量但不改变任务成败 | 成功提示 1 s 就消失且无 aria-live；禁用按钮没有原因说明 |

定级看的是"在真实场景里的后果"，不是"违反了几条规范"。一个问题如果用户根本不会遇到（场景不存在），再规范也不报。

**频率不自动降级**：入口来自正常路径、分享或收藏，且失败后没有恢复路径，就按后果定级；"发生概率低"只影响排序与是否值得单独报告，不把死胡同降成打磨项。

**数字、时间、口径错误按 P1 起**：页面展示的数与导出、下钻、分析对不上，或同一字段在不同入口含义不同，读者可能据此对外引用或做编辑判断；仅仅格式不统一是 P2。

**同类动作的不同落点**：会让用户按错误含义行动（如"焦点"栏放的是单篇报道）→ P1；只是多点一步或命名不统一 → P2。

**兄弟视图的结构差异**：同一路由的两个视图（如 `?tab=latest` 与 `?tab=ai`）或兄弟入口，仅因调用参数不同导致页头/操作位置不一致 → P2；导致返回或页级操作更难发现、或让用户误判页面层级 → P1。

**重复提交的升级条件**：会产生不可逆副作用（重复下单、重复扣款、重复创建且服务端无幂等）→ P0；有服务端幂等或后果可恢复 → P1。示例里的设置保存是幂等覆盖，定 P1；支付/下单定 P0。

**组件脱离页面时**：按"数据完整性 / 误导性成功"判断——提交未校验数据、失败显示成功、成功后永久不可再提交、失败清空输入，都按 P0 处理，并在报告开头写清假设。

## 3. 常见误报

- **从截图推断行为**：截图里看不出 hover、focus、键盘、请求失败后的样子。不要写"点击没有反馈"，除非你看了代码或真的点了。
- **把规范当法律**：44 px 触控热区是移动端的经验值，桌面鼠标场景下 24 px 也可用；先把场景说清楚。
- **忽略业务约束**：强制登录可能是商业决定。指出代价（比如游客无法比价），而不是宣布它"违反最佳实践"。
- **把审美当可用性**："这个渐变不好看"不是交互问题。
- **只报问题不给场景**："没有 loading"要补上"在网络慢时用户会连点三次，产生三笔订单"才是完整判断。
- **同一根因拆成十条**：十个按钮都缺 focus 样式，合并成一条，列出位置清单。
- **把数据形态当缺陷**：快照过期、无权限、无对照期时看到的空或回退，不代表功能坏了；先确认数据形态，再判断是缺陷还是限制。
- **把项目既定设计当缺陷**：先读项目自己的状态/设计文档与规则；违反项目承诺的行为优先报，与通用规范冲突但项目明确选择的，写清代价而不是判违规。

## 4. 常见 P0 模式

先查这几类，它们比样式问题更常造成真实损失：

- 成功一次后状态不复位，第二次操作被禁用且无说明（用户只能刷新，丢失输入）。
- 失败后清空表单或离开当前页（输入丢失且不可恢复）。
- 请求进行中可重复提交（重复下单、重复扣款）。
- 不可逆操作（删除、注销、发布）无撤销、无后果说明。
- 键盘用户完全无法完成主任务（可点元素不可聚焦、弹窗无焦点管理）。

## 5. 示例：保存按钮

⚠️ 这个示例用来校准**格式与分级尺度**，不是待检清单。真实走查里不要照抄它的四条；先看代码，再按实际证据新增。

输入（用户给了一段代码，说"保存按钮感觉怪怪的"）：

```jsx
function SaveButton({ values }) {
  const [saved, setSaved] = useState(false);
  async function save() {
    const res = await fetch("/api/settings", {
      method: "POST",
      body: JSON.stringify(values),
    });
    if (res.ok) setSaved(true);
    else alert("保存失败");
  }
  return (
    <button onClick={save} disabled={saved}>保存</button>
  );
}
```

输出（节选——只演示分级与格式，示例代码中的 `try/catch`、`Content-Type`、`res.ok` 业务判定不在本例展开，检查方法见 §1）：

**结论**：主风险是保存一次后按钮永久禁用（P0），以及请求期间可重复提交、失败后没有恢复路径；最值得先改的是把 `saved` 布尔量换成状态机。

| # | 严重度 | 位置 | 问题 | 影响 | 修法 |
|---|---|---|---|---|---|
| 1 | P1 | `SaveButton.jsx:11` | 请求期间按钮不禁用、无 pending | 网络慢时连点会产生重复请求，设置被后一次覆盖 | 增加 `status` 状态，pending 时按钮内 loading 且禁用 |
| 2 | P1 | `:8` | 失败用 `alert`，无原因、无重试 | 用户不知道是网络还是校验问题，只能重试或放弃 | 改为表单内错误条：原因 + 重试按钮，保留已填内容 |
| 3 | P0 | `:12` | 成功后按钮永久禁用，编辑字段也不复位；文案仍是"保存" | 第一次保存后，用户再改任何字段都无法保存，只能刷新并丢失输入；且无法确认是否保存成功 | `status` 状态机 + `dirty`；成功态显示"已保存"+ 时间，编辑后回到可保存 |
| 4 | P2 | `:11-12` | 状态变化没有读屏告知 | 读屏用户不知道保存结果 | 结果区加 `role="status"` |

**验收动作**：断网后点保存 → 应看到错误原因与重试；恢复网络点重试 → 应看到"已保存"；连续快速点击 → 应只有一个请求。

## 6. 报告写作

- 结论先写风险与第一优先项，别让人读十页才明白。
- 每条问题都能被单独拿去改：位置精确、修法具体到状态或文案。
- 修法给"最小可行改动"，再给"如果重构可以怎么做"。
- 涉及设计取舍时给出代价，不要只给答案：可撤销 vs 二次确认，哪种更适合这个业务。
- 最后给验收动作，让改动可被验证，而不是"改完看看"。
- 全项目/多入口走查：主报告只放合并结果与未解决难点，分册、原始证据与截图进附录；有过往评审时加一张「基线问题回归」表（问题 / 基线证据 / 现状 / 新证据），比重新列一遍更有用。
