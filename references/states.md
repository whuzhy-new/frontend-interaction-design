# 状态与反馈规格

交互缺陷大多不是"长得不对"，而是"少画了一个状态"。这份文档给出可直接填进规格表的结构。

## 0. 术语与基线

**状态词汇（全库统一用这一套，不要另造同义词）**

- **操作型元素**：默认 / 悬停 / 聚焦 / 按下 / 禁用 / 进行中 / 完成后。
- **异步数据**：初始 / 加载 / 成功 / 空 / 成功 / 失败 / 超时 / 无权限 / 离线（"部分成功"是其中一种结果状态）。
- **容器**：关闭 / 打开 / 进行中（如提交）/ 完成。
- 「部分成功」是状态，「部分失败」是结果描述；同一份文档里二选一，不要混用。

**尺寸与时长基线（经验值，不是合规判据）**

| 项 | 建议 | 依据与边界 |
|---|---|---|
| 触控目标 | WCAG 2.2 AA（SC 2.5.8）最低 **24×24 CSS px**，允许间距等例外；AAA（SC 2.5.5）为 **44×44** | 面向触屏可把 44×44 作为设计目标（Apple HIG 44pt、Material 48dp），但不要说成 AA 要求 |
| 物理尺寸 | NN/g 建议约 1cm×1cm | 1cm ≈ 37.8 CSS px，与 44 px 不等值，不要并列成同一个数 |
| 按下反馈 | ≤ 100 ms | 直接操纵感；无即时响应会被重复点击 |
| 加载提示 | 300 ms – 1 s 后出现 | 少于 300 ms 不显示，避免闪烁 |
| 长任务 | > 10 s 转后台 + 通知 | 允许离开，回来能看结果 |
| 动效 | 100–300 ms（按平台与距离调整） | 尊重 `prefers-reduced-motion` |
| 撤销窗口 | 5–10 s（但见 §6） | 仅靠 toast 可能构成 WCAG 2.2.1 时限问题 |

## 1. 可交互元素的五态

| 状态 | 用户的问题 | 必须能看出什么 |
|---|---|---|
| 默认 | 这能点吗？ | 可交互的视觉信号（对比、形状、指针） |
| 悬停 | 点了会怎样？ | 目标确认；不承载关键信息 |
| 聚焦 | 键盘现在在哪？ | 清晰、与背景有对比的焦点环；不可移除 |
| 按下 | 系统收到了吗？ | 100 ms 内的即时响应（位移、颜色、涟漪） |
| 禁用 | 为什么不能点？ | 弱化 + 说明原因与恢复条件 |

补充两个常被漏掉的状态：

- **进行中**：异步操作触发后的状态，按钮内 loading、禁止重复提交、保留布局避免跳动。
- **完成后**：短暂的成功反馈（1–3 s 自动消失），或结果状态（列表新增一行、按钮变为已完成）。

只靠颜色区分的状态对色觉障碍用户无效，要配合形状、图标或文案。

## 2. 异步状态矩阵

每个异步操作按行填，缺一行就是一个潜在缺陷。

| 状态 | 界面表现 | 文案 | 可执行动作 |
|---|---|---|---|
| 初始 | 尚未请求，展示引导或占位 | — | 触发请求 |
| 加载 | 骨架/进度/按钮内 loading | 超过 1 s 给"正在…" | 取消（可取消时） |
| 成功 | 结果 + 位置稳定 | 一句确认，不用"成功！"刷屏 | 下一步 |
| 空 | 说明为什么空 | "还没有 X" + 下一步 | 创建、清筛选、看示例 |
| 部分成功 | 分开呈现成功与失败项 | "3 项已保存，2 项失败" | 只重试失败项 |
| 失败 | 保留已填内容，错误定位 | 发生了什么 + 怎么办 | 重试、修改、联系支持 |
| 超时 | 与失败区分，说明可能已在后台完成 | "响应超时，可能已提交" | 查看状态、重试（防重复） |
| 无权限 | 说明缺什么权限、怎么获得 | 角色/申请入口 | 申请、切换账号 |
| 离线 | 顶部状态条，不阻塞阅读 | "已离线，修改将在联网后同步" | 继续浏览、手动重试 |

## 3. 加载策略选择

用户对等待的感知取决于"有没有进展"，不是绝对时长。

| 预计时长 | 推荐 | 避免 |
|---|---|---|
| < 300 ms | 不显示任何 loading（闪烁比等待更烦） | spinner 一闪而过 |
| 300 ms – 1 s | 按钮内 loading / 局部 spinner | 全屏遮罩 |
| 1 s – 10 s | 骨架屏（结构可预期时）或进度条 | 无信息的转圈 |
| > 10 s | 后台任务 + 完成通知 + 可离开 | 锁死页面等它转 |

骨架屏要和真实布局同构，否则内容到达时会跳动；跳动的代价比多等 200 ms 更大。

## 4. 空状态

空状态是教学位，不是"没数据"的告示牌。分四类，文案与动作都不同：

| 类型 | 场景 | 应该给 |
|---|---|---|
| 首次空 | 新用户还没有内容 | 这是什么 + 第一条怎么建（示例或模板） |
| 清空 | 用户删完了 | 确认结果 + 恢复入口（回收站、撤销） |
| 无结果 | 搜索/筛选没有命中 | 改关键词、放宽条件、浏览分类 |
| 无权限 | 有数据但看不到 | 说明原因 + 申请/切换路径 |

反面例子：`暂无数据`。它回答了"为什么空"吗？给了下一步吗？

## 5. 错误文案公式

**发生了什么 + 为什么 + 怎么办。** 三要素缺一，用户就只能试错。

| 差 | 好 |
|---|---|
| 输入有误 | 邮箱格式不完整，需要包含 @ 和域名，例如 name@company.com |
| 操作失败 | 保存失败：网络中断。你的修改已保留，恢复网络后点"重试" |
| 密码不符合要求 | 密码需要至少 12 位，且包含一个数字；你目前是 9 位 |
| 系统错误 (500) | 服务暂时不可用，我们已记录。请 2 分钟后重试，或复制错误码 A1B2 联系支持 |

原则：
- 不用错误码替代人话，但可以附上错误码便于支持排查。
- 不要把责任推给用户（"您输入了非法字符"），描述事实与修法。
- 错误出现的位置要贴近出错字段；表单顶部汇总只作为补充。
- 已填内容必须保留——清空表单是最容易被记住的糟糕体验。

## 6. 破坏性操作

决策顺序：

1. **能撤销吗？** 能 → 直接执行 + 撤销（5–10 s 的 toast，或持久回收站）。删除到回收站优于弹窗确认。

   只靠 5–10 s 的 toast 做唯一恢复入口，会构成 WCAG 2.2.1 的时限问题：提供持久撤销（回收站/历史）、可暂停的 toast，或键盘可达的撤销按钮；业务影响大的操作不要依赖自动消失的提示。
2. **不能撤销，但影响可预览？** → 显示影响范围（"将删除 3 个项目，包含 1 个共享链接"），再确认。
3. **不可逆且影响大？** → 阻断式确认，要求输入名称或勾选确认，且确认按钮文案写清后果（"删除并清空回收站"），不用"确定/取消"。

确认弹窗的三个常见错误：默认焦点在危险按钮上、危险按钮与安全按钮视觉权重相同、文案只问"确定吗"。

## 7. 并发与竞态

- 同一操作重复提交：提交瞬间禁用 + 幂等键（服务端也要防）。
- 快速切换筛选/搜索：取消上一个请求（AbortController），并丢弃过期响应，避免旧结果覆盖新结果。
- 乐观更新：先改 UI，失败时回滚并说明；只用于高成功率、可回滚的操作（点赞、勾选、排序）。
- 超时：`AbortController` 只是取消原语，**不提供超时**。设置超时要用 `AbortSignal.timeout(ms)`，或用 `setTimeout` 调 `abort()`；需要同时支持用户取消时用 `AbortSignal.any([...])`。区分 `AbortError`（取消）与 `TimeoutError`（超时）。
- 超时重试：区分"请求发出但响应丢失"与"请求未发出"，前者重试前先查询状态，避免重复扣款/重复创建。abort 只取消客户端等待，不保证服务端没执行，写操作不能靠 abort 防重复。

## 8. 焦点、模态与键盘

**两条实现路径，选一条，不要混着做：**

1. **原生 `<dialog>` + `showModal()`**：已提供模态语义、焦点约束与背景 inert。不要再手工加 `role="dialog"`、`aria-modal` 或重复焦点陷阱；只需给可访问名称（`aria-labelledby` 指向标题）并在关闭后把焦点还给触发元素。
2. **自定义对话框**：`role="dialog"` + `aria-modal="true"` + `aria-labelledby`/`aria-label`；打开时焦点移入；把**背景兄弟节点**设为 `inert`（不要把 dialog 的祖先设为 inert）；不支持 inert 的旧浏览器用焦点陷阱兜底。

**关键区别**：`aria-hidden` 只把内容移出无障碍树，**不阻止 Tab 和点击**，不是 `inert` 的替代。`aria-modal="true"` 是语义承诺，只有真的阻断外部交互时才写；写了但键盘仍能 Tab 出去，比不写更糟。

**关闭路径与未保存内容**（统一按这张表）：

| 关闭方式 | 无未保存内容 | 有未保存内容 |
|---|---|---|
| Esc | 关闭 | 弹「放弃修改？」确认，或保留草稿 |
| 点遮罩 | 关闭 | 不关闭（提示有未保存内容） |
| 关闭按钮 | 关闭 | 弹确认 |
| 完成后自动关 | 关闭并给结果 | — |

**其余键盘规则**：列表/表格支持方向键或给出说明；不要拦截浏览器快捷键；长页面提供跳过导航链接。

**页面级错误的播报**：错误用 `role="alert"`（自带 assertive/atomic），成功与进度用 `role="status"`（polite）。live region 必须**先存在于 DOM**，再更新内容；同时把焦点移到错误摘要或第一个无效字段，并提供 `aria-invalid`/`aria-describedby` 关联。不要用单独的 `aria-live="assertive"` 替代 `role="alert"`。

## 9. 状态文案速查

| 场景 | 不要写 | 建议写 |
|---|---|---|
| 加载 | 加载中… | 正在保存草稿…（超过 1 s 时） |
| 成功 | 操作成功 | 已发布，可在「我的文章」查看 |
| 空 | 暂无数据 | 还没有项目。创建第一个项目，或从模板开始 |
| 失败 | 系统错误 | 保存失败：网络中断。修改已保留，联网后重试 |
| 禁用 | （无说明） | 需先填写收货地址才能提交 |

## 10. 反馈强度与组件

反馈不是「弹个提示」：三个判断决定用什么组件——**会不会挡住用户、会不会消失、用户需不需要对它做动作**。

| 场景 | 强度 | 首选 | 不要用 |
|---|---|---|---|
| 操作成功/失败的轻量告知 | 低 | Message / Toast | Modal |
| 系统主动通知（异步完成、有新版本） | 中 | Notification | Message |
| 页面内常驻说明（表单顶部、离线、试用到期） | 中 | Alert / Banner | Message |
| 需要用户做决定/确认 | 高 | Modal / Popconfirm | Toast |
| 整页结果（成功页、403/404/500） | 高 | Result | Alert |
| 等待（可预估） | 低 | Progress / Spin | 空白页 |
| 等待（结构可预期） | 低 | Skeleton | 全屏 spinner |

关键约束：

- **Message/Toast 默认 3 秒左右消失**，只承载「无需操作」的短结果；重要失败通知不要用它。
- **Notification 右上角、可手动关闭**（默认 4.5 秒左右），适合用户可能不在当前页面的异步通知；同屏最多 2–3 条。
- **Alert 常驻、不自动消失**，可带关闭按钮；关掉后要有再次看到的路径（状态变化时重现）。
- **Modal 只有在传递非常重要且可操作的信息时才用**；失败时避免不必要的提醒弹窗。
- **Popconfirm** 用于目标元素附近的轻量确认，比全屏模态打断更小。
- **Tooltip** 只描述被指向对象，不承载复杂文本与操作；**Popover** 才能放链接/按钮。

同一次操作不要同时弹 Message + Notification + 刷新列表三处反馈；选一处主反馈，其余保持安静。

## 11. 数据与 AI 的状态扩展

通用异步状态不够用时，补这两组。

**数据界面**

| 状态 | 界面表现 | 用户动作 |
|---|---|---|
| 数据未就绪 | 上次结果 + 预计更新时间 | 等待、看历史、订阅 |
| 部分数据 | 标明缺哪段/哪个渠道 | 看已有部分、重试 |
| 数据延迟 | 截止时间 + 原因 | 看旧值并标注、刷新 |
| 口径变更 | 变更说明、生效日、新旧对比 | 切口径、读变更记录 |
| 样本不足 | 样本量 + 仅供参考 | 扩大范围、换时间段 |

**AI 输出**

| 状态 | 界面表现 | 用户动作 |
|---|---|---|
| 生成中 | 流式输出 + 停止 | 停止、改写 |
| 成功 | 结果 + 来源/依据入口 | 采纳、编辑、复制 |
| 内容可疑 | 低置信标注、缺来源提示 | 查看依据、换范围重试 |
| 被拦截 | 说明触发哪条策略 | 改写、申诉/转人工 |
| 失败 | 可执行原因 + 重试 | 重试、换输入 |
| 已撤销 | 明确“已撤销”与恢复入口 | 恢复、重新生成 |

原则：**低置信不能只加一句免责声明**，要给验证入口；数据状态不能混成空态。
