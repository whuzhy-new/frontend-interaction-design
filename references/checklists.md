# 交互检查清单

按维度分组，每条是一个可以直接回答"是/否"的判定问题。"否"不等于有问题——先确认场景是否适用，再定级。完整用法见 [review.md](review.md)。

## 1. 状态覆盖

- [ ] 异步操作是否覆盖：初始、加载、成功、空、部分成功、失败、超时、无权限、离线？（完整矩阵见 states.md §2）
- [ ] 列表是否覆盖：首次空、筛选后无结果、只有部分数据、数据过期？
- [ ] 是否有"操作进行中"的界面状态，还是只把按钮变灰？
- [ ] 刷新、返回、断网、重复提交后，界面是否还能说出当前真实状态？
- [ ] 长任务是否有进度或可离开的说明，而不是让用户盯着 spinner？

## 2. 反馈与感知

- [ ] 按下（pointerdown）到视觉响应是否小于 100 ms？没有即时响应的按钮会被重复点。
- [ ] 操作结果是"成功"还是"失败"，用户不滚动、不猜测就能看到吗？
- [ ] 破坏性操作完成后，是否给了撤销或明确的完成确认？
- [ ] 后台操作（保存草稿、同步）的结果是否有不打扰的告知？
- [ ] 同一操作重复触发的防护是禁用 + 说明，还是静默吞掉？

## 3. 表单

- [ ] 每个字段都有可见标签（placeholder 不是标签）？
- [ ] 必填与可选是否一致标注，且不靠星号颜色区分？
- [ ] 校验时机是否合理：失焦后校验、提交时汇总，而不是边输边报错？
- [ ] 错误信息是否指向具体字段、说明原因、给出修法，并保留已填内容？
- [ ] 密码规则是否在输入前说明？
- [ ] 提交按钮是否覆盖：可提交 / 提交中 / 失败可重试？
- [ ] 离开页面时是否有未保存提示（仅在真的有未保存内容时）？
- [ ] 自动填充（autofill）是否被破坏，比如禁用了粘贴或使用了非标准字段名？

## 4. 控件选型

- [ ] 按钮触发动作、链接跳转页面，两者没有混用？
- [ ] 多选、单选、开关的使用是否符合语义（开关用于立即生效的二选一）？
- [ ] 下拉是否只用于选项多、且不需要用户对比的场景？
- [ ] 标签页用于同级切换，且没有把必须顺序阅读的内容做成标签？
- [ ] 折叠面板是否避免了"多数内容都要看"的场景？
- [ ] 模态是否只用于必须打断的决策，而不是承载普通表单？
- [ ] 禁用控件是否说明了原因和恢复条件？

## 5. 导航与可发现性

- [ ] 用户能否随时回答：我在哪、我能去哪、怎么回去？
- [ ] 高频目标是否直接可达，而不是藏在两级菜单里？
- [ ] 可点击元素看起来能点吗（悬停、指针、视觉重量）？
- [ ] 空结果页是否给了替代路径（改关键词、浏览分类、联系人工）？
- [ ] 站内返回、浏览器返回、刷新之后，筛选、已加载批次、滚动位置与焦点是否恢复？
- [ ] 图标按钮是否有文字标签或 tooltip？

## 6. 动效

- [ ] 每个动效都有目的（引导注意、说明因果、表达状态），而不只是"有质感"？
- [ ] 时长是否在 100–300 ms（大范围转场可更长），并且不阻塞操作？
- [ ] 是否尊重 `prefers-reduced-motion`？
- [ ] 动效是否可中断（用户快速操作时不会排队播放）？
- [ ] 是否没有滚动劫持、没有强制视差、没有自动轮播？

## 7. 触屏与移动

- [ ] 点击热区是否满足 WCAG 2.2 AA：至少 24×24 CSS px（2.5.8，含间距例外）？触屏场景是否达到 44×44 的设计目标（AAA 2.5.5）？
- [ ] 主要操作是否在拇指可达区？
- [ ] 手势（滑动、长按）是否有可见替代入口？
- [ ] 是否处理了键盘弹起、安全区、横竖屏切换？
- [ ] 滑动删除等操作是否有误触防护与撤销？

## 8. 复杂应用与数据

- [ ] 批量操作是否显示了"选中了多少、会影响什么"？
- [ ] 表格的排序、筛选、分页状态是否可分享/可恢复？
- [ ] 是否有键盘快捷键，且不与浏览器/读屏快捷键冲突？
- [ ] 数据密集界面是否提供密度切换或列显隐？
- [ ] 长流程是否可保存草稿、可断点续填？
- [ ] 每个指标是否能看到口径、来源、更新时间、对比期？
- [ ] 数据未就绪/部分数据/口径变更是否有独立状态，而不是显示 0 或空？
- [ ] 数据权限三层（指标、导出/API、加工后）是否都有对应表达？
- [ ] 导出/自助查询是否有权限、审计与上限？
- [ ] 时区、截止时间、默认时间范围是否写清？
- [ ] 界面计数、分析计数、下钻样本与导出条数能否互相对上；折叠、去重、打包造成的差异是否就地标注？
- [ ] 同一能力在多个入口（如全站数读与筛选内分析）的默认时间窗与样本范围，是否就地说明差异？

## 9. AI 界面

- [ ] 生成过程是否可见（流式输出、停止按钮）？
- [ ] 用户能否重试、改写、换模型/换范围，而不必重头再来？
- [ ] 不确定或可能错误的输出是否有标注与来源？
- [ ] 失败（超时、限流、内容拦截）是否给出可执行的下一步？
- [ ] 是否说明了对输入的使用方式（尤其涉及上传数据时）？
- [ ] 是否区分生成中/成功/内容可疑/被拦截/失败/已撤销，而不是只有成功与失败？
- [ ] 低置信或可疑内容是否给出验证入口（来源、换范围、人工确认）？

## 10. 无障碍（交互部分）

- [ ] 所有交互元素键盘可达，焦点可见？
- [ ] 弹窗/抽屉是否锁定焦点、Esc 关闭、关闭后焦点回到触发元素？
- [ ] 动态内容更新是否有 `aria-live` 或等效告知？
- [ ] 状态（错误、选中、禁用）是否不只靠颜色传达？
- [ ] Tab 顺序是否与视觉顺序一致？
- [ ] 文本对比度 ≥ 4.5:1（大文本 ≥ 3:1），UI 组件与焦点指示 ≥ 3:1（WCAG 1.4.3 / 1.4.11）？
- [ ] 焦点指示可见、不被遮挡，且有等效替代（不要求必须是 outline）？
- [ ] 局部 CSS 是否覆盖了全局 `:focus-visible`（搜索框、输入框最常见）？

## 11. 欺骗性模式与伦理

- [ ] 没有"确认羞辱"（确认按钮写"不，我不想省钱"）？
- [ ] 没有隐藏费用、预勾选、诱导订阅？
- [ ] 退订/注销/取消是否和开通一样容易？
- [ ] 默认选项是否对用户有利，而非对转化率有利？
- [ ] 限时、库存等稀缺信息是否真实？


## 12. 深色主题（dark mode）

- [ ] 深色下的文本对比度是否重新验证（不是把浅色值反过来）？
- [ ] 状态色（错误/成功/警告）在深色下是否仍可辨，且不与品牌色混淆？
- [ ] 图片、插图、阴影、遮罩在深色下是否发灰或丢失层级？
- [ ] 是否尊重系统偏好（`prefers-color-scheme`），并提供手动切换与「跟随系统」？
- [ ] 切换主题时是否避免闪烁（首屏前应用主题，或使用 CSS 变量）？
- [ ] 深色不是简单反色：大面积纯黑 + 纯白会眩光，通常用深灰背景 + 降饱和前景。

## 13. 实现一致性

- [ ] 新增组件前搜过现有组件/变体，没有重复实现？
- [ ] 优先用现有组件 + variant/组合，而不是复制改名？
- [ ] 样式只用 token：没有裸 hex/rgb、裸 px（间距/字号/圆角/阴影）、裸 font-family、裸 z-index？
- [ ] 缺 token 时新增了语义 token 并注明用途，没有在组件里写魔法值？
- [ ] 页面没有选择器命中共享组件内部、没有 `!important` 覆盖？
- [ ] 变体用 variant/prop 表达，没有用大量 boolean 开关拼职责？
- [ ] 同一 UI 元素只有一个组件来源（无同名/同结构两处实现）？
- [ ] 修改共享组件后，所有引用入口都做了回归？
- [ ] 新代码的关键状态（加载/空/失败/禁用/选中/展开）是否补齐？
- [ ] 硬编码扫描结果是否逐条处理（token / 结构性值 / 漏网）？
- [ ] 同一功能在多入口是否有对照表（职责/状态/操作/数据/视觉/外部影响）？
- [ ] 同一路由的不同视图（`?tab=`、`?view=`、筛选状态）与兄弟入口，页头结构（返回、标题、页级操作）是否一致？同一共享组件的同类调用是否传了相同的布局参数/变体？
- [ ] 统一时是否写明保留的差异与理由，而不是强行全站一个样？

## 用法提醒

清单是扫描工具，不是交付物。报告里只保留"有证据 + 有影响 + 有改法"的条目；同一根因的多条问题合并成一条，避免把一份报告写成一本书。
