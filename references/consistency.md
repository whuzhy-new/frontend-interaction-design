# 实现一致性：写码约束与按功能统一

用于两类任务：写/改前端代码时守住组件复用与 token；多个入口同一功能不一致时做盘点与统一。共同标准：**同一功能只有一个实现来源；样式只走 token；改一处，所有入口一起正确变化。**

## Part A. 写码约束

### A1. 先找再写

1. 搜组件目录/索引/Storybook/使用示例，确认是否已有同职责组件或变体。
2. 按语义搜，不只按名字：`card`、`list-item`、`result`、`empty`、`toolbar`、`filter-bar`。
3. 查 token：现有语义 token 能否表达这次的颜色/间距/字号/圆角。
4. 查页面覆盖：目标页面有没有对共享组件做局部 CSS 覆盖。

**复用顺序**（能停就停）：现有组件 → 加 variant/prop/slot → 用现有组件组合 → 新建变体 → 新建组件。
新建组件必须写一句「为什么现有组件不够」，否则视为重复实现。

### A2. 新建与变体门槛

- 同时满足才新建：职责不同且变体表达不了；至少 2–3 处复用或明确是产品差异；有独立状态集或交互规则。
- 只换颜色、间距、圆角、标题层级的，用 variant 或 token，不新建组件。
- variant 只表达产品差异（主/次、紧凑/宽松、只读/可编辑），不表达页面差异。
- 超过 3 个 boolean prop 或 5 个 variant 值，先重新划边界；参数说不清就是边界错了。
- 页面差异用布局容器或组合解决，不往共享组件塞页面专属 prop。

### A3. 样式只走 token

禁止写死：`#1677ff`、`rgb()/hsl()`、裸 `px`（间距/字号/行高/圆角/阴影）、裸 `font-family`、裸 `z-index`。
允许：CSS 变量/主题 token、0/100%/auto、引用 token 的 `calc()`。

缺 token 时：先加**语义 token**（用途命名，如 `color-text-secondary`、`space-card-gap`），再在组件里引用；组件只用 semantic/component token，不直接引 primitive。
token 三层：primitive（原始值）→ semantic（用途）→ component（组件专用）。

### A4. 页面覆盖

- 禁止页面 CSS 选中共享组件内部结构（`.page .card .title`、`.ant-btn`）或 `!important`。
- 需要不同布局时，用外层容器控制布局，用 variant 控制外观。
- 确需覆盖时，先确认是不是组件缺 variant；补 variant，不留页面级补丁。

### A5. 反例对照

| 反例 | 问题 | 正确做法 |
|---|---|---|
| 复制 Card 改个名 `NewsCard2` | 两份实现，改一处漏一处 | 给原组件加 variant 或 slot |
| 页面里 `.page .card { padding: 8px }` | 覆盖共享组件，其他入口不一致 | 加 `size` variant 或外层容器 |
| `color: #666` | 主题切换/暗色失效 | `var(--color-text-secondary)` |
| 加 3 个 boolean 拼 4 种形态 | 参数爆炸、职责混乱 | 拆成 variant 或两个组件 |
| 同名组件存在两处 | 调用方随机引用 | 删除一份，统一导出 |

### A6. 写后自检

1. **重复**：新组件/新样式是否与现有同名、同结构、同视觉？搜名称 + 搜关键 class/结构。
2. **硬编码**：跑本 Skill 的 `check_hardcodes.py <路径>`（参数是项目路径），逐条判断是 token、结构性值还是漏网。
3. **覆盖**：diff 里有没有页面级选择器命中共享组件内部。
4. **回归**：改了共享组件，所有引用入口是否都过一遍（见 B7）。
5. **状态**：新组件是否补齐默认/加载/空/失败/禁用/选中/展开。

**交付改动说明三行**：用了哪个现有组件/变体；没有则写为什么新建；新增/使用的 token；自检与回归结果。

## Part B. 按功能统一

### B1. 三条纪律

1. **按功能盘点，不按文件盘点**：从用户任务出发（浏览、切换范围、筛选、提交、展开），再找各入口实现。
2. **先写统一规则，再改代码**：先定共同职责、统一行为、允许变化，再决定用哪个实现。
3. **差异要显式**：产品差异（栏目专属切换）保留；页面差异（容器、参数、CSS 覆盖）消除或收敛为 variant。

### B2. 功能盘点

| 项 | 记录 |
|---|---|
| 功能 | 用户要完成什么（如「切换内容范围」） |
| 入口 | 出现在哪些页面/弹窗/端 |
| 实现 | 组件文件、调用参数、容器、页面级 CSS |
| 行为 | 点击/键盘/触屏/返回/重试 |
| 状态 | 默认/加载/空/失败/禁用/选中/展开 |

从用户操作出发，才能发现「不同名字的同一功能」和「同一组件被不同容器包出不同结果」。

### B3. 六维对照

| 维度 | 检查什么 |
|---|---|
| 职责与内容 | 帮用户完成什么任务、展示哪些必要信息 |
| 状态 | 默认、加载、空、失败、禁用、选中、展开 |
| 操作行为 | 点击、键盘、触屏、返回、取消、重试 |
| 数据行为 | 请求时机、并发、取消、分页、缓存、竞态 |
| 视觉布局 | 字号、行高、间距、宽度、图片、响应式 |
| 外部影响 | 父容器、全局 CSS、页面覆盖、调用参数 |

每条判断要能指到实际页面和代码位置；只写「不一致」不算证据。

### B4. 分级：哪些该合、哪些该留

| 类型 | 判断 | 处理 |
|---|---|---|
| 真重复 | 同职责、多份实现 | 收敛为共享组件 |
| 名义复用但偏差 | 同一组件，容器/参数/CSS 覆盖导致表现不同 | 改调用方式或加 variant |
| 假重复 | 看起来像，职责不同 | 不合并 |
| 合法差异 | 产品/场景明确不同（栏目专属切换、权限差异） | 保留，写清理由 |

### B5. 统一规则（改代码前先写）

对每组重复实现写四句：**共同职责**、**统一行为**（状态/交互/文案/数据哪些必须一致）、**允许变化**（由 variant/props 表达）、**采用实现**（以哪份为准，其余怎么迁移）。
参数膨胀检查：需要大量 boolean 拼职责、variant 值超过 5 个，先拆再合。

### B6. 按重复位置选改法

- 展示结构重复 → 共享组件；
- 状态/交互逻辑重复 → 共享 hook/逻辑模块；
- 数值/样式规则重复 → 统一 Token；
- 调用参数、容器、页面覆盖造成偏差 → 改使用方式，统一入口；
- 只有少数稳定差异 → 显式 variant。

### B7. 沿真实入口验收

- 列出该功能的所有入口（页面、弹窗、抽屉、移动端）。
- URL 变体也算入口：同一路由的 `?tab=`/`?view=`/筛选状态与兄弟入口要成对验收，并排截图比较页头四件套（返回入口、页标题、页级操作、第一条内容起点）的相对位置。
- 每个入口验证：默认、加载、空、失败、禁用/选中；桌面与移动；键盘与触屏。
- 数据类再验：快速切换、连续点击、失败重试、返回顺序。
- 改共享组件后，所有入口回归；视觉变化留截图；没验的写「待确认」。

**通过标准**：同一功能在不同入口遵循同一规则；改一处后，相关入口一起正确变化。组件数量减少只是结果，不是目标。

### B8. 最小交付（四段，能表格就别写长文）

1. **功能组件地图**：功能 → 入口 → 实现。
2. **重复与差异清单**：证据、影响、优先级、保留理由。
3. **统一规则**：共同职责、统一行为、允许变化、采用实现。
4. **验收记录**：入口 × 状态 × 端，已验证/待确认。

### B9. 什么时候停

- 差异用户感知不到、统一成本大于收益；
- 职责确实不同（假重复）；
- 统一后参数越来越难理解——该拆成两个组件，而不是继续加开关。

## 走查时怎么查

按 [checklists.md](checklists.md) §13 逐项查：重复组件、硬编码、页面覆盖、变体滥用、单来源、共享组件回归、状态补齐、扫描结果处理。全项目走查时先按用户旅程切分，再按功能横向对照；同一动作、同一数据字段在不同入口不一致，按 B2–B5 盘点，不要在每个页面各报一遍。定级沿用 [review.md](review.md) 的 P0/P1/P2：重复实现导致「改一处漏一处」、硬编码导致主题/暗色失效、页面覆盖导致跨页不一致，按影响面定 P1；只影响代码整洁、无用户可见差异的 P2。
